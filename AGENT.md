# AGENT.md: rules for anyone (human or tool) working on Smaran

This file turns the research in [`Research Work/`](Research%20Work/00_MASTER_RESEARCH_INDEX.md) into working rules. Read it before you change code, docs, commits or the demo. If a rule here conflicts with an older doc, this file wins; if it conflicts with the research, fix this file and say why in the commit.

Project: **Smaran (ΣMARAN)**, Code Cubicle 6.0, Problem Statement 3 (owned by Qdrant). Current audit and work plan: [`docs/AUDIT_AND_PLAN.md`](docs/AUDIT_AND_PLAN.md).

## 0. Rule zero: no tool attribution, anywhere

- Never mention the AI assistant or its vendor used to help build this project. That means no assistant or vendor names, no "generated by / written with" lines, no `Co-Authored-By` trailers, no robot emoji or tool links.
- This applies to **everything**: source code, comments, docstrings, docs, README, research files, commit messages, PR titles and bodies, branch names, tags, file names, slides, LinkedIn posts, and the submission form.
- Commits are authored by the team member who did the work, from their own GitHub account.
- Before every commit, run the check in §9 and make sure it prints nothing.

## 2. The PS3 contract (never break these)

Every change must keep all ten requirements true. Full matrix: `Research Work/02_PROBLEM_STATEMENT_3_ANALYSIS.md` §2.

1. **R1: Qdrant Edge is the on-device engine.** Use `qdrant-edge-py` (`EdgeShard`), never `qdrant-client` local mode, on the device. `qdrant-client` is allowed only in the gateway (talking to Qdrant Server) and in tests.
2. **R3: hybrid search** (dense + BM25, RRF) stays the default query path.
3. **R4: decisions are dynamic and explained.** Every memory carries `decision {residency, criticality, confidence, by, reason}`.
4. **R5: the device works with the link off.** No device code path may require the network.
5. **R6: sync targets a real Qdrant Server.** Embedded mode is a fallback for dev, tests and emergencies, not the demo default.
6. **R7: conflicts are flagged, never guessed.** Concurrent versions become `contested`; only a supervisor resolves them. No timestamp or last-writer-wins logic anywhere.
7. **Krypta has no sync code path.** Do not add one, not even behind a flag.
8. **PII rules run before any model** and cannot be overridden by the classifier.
9. **R8: the UI covers memory, search, sync status and activity.**
10. **R9: not "just a local vector database".** The cloud must give something back to the edge (Agora mirror, change feed, escalation).

## 3. Stack and pins

- Do **not** change the stack (`Research Work/13_TECH_STACK_RECOMMENDATION.md`).
- `qdrant-edge-py==0.8.0` stays pinned until after the final. Don't upgrade unless a bug forces it.
- Pin one compatible `qdrant-client` / `qdrant/qdrant` image pair and document it in the README.
- Models must load offline after `scripts/setup_models.py` (`HF_HUB_OFFLINE=1`).
- Python 3.10+, FastAPI, SQLite WAL, React + Vite + TypeScript. No new runtime services.

## 4. Do not build (`Research Work/11_WHAT_NOT_TO_BUILD.md`)

- ~~No local LLM chat~~ **Superseded 30 Sep 2026** by the personal-companion pivot ([docs/ARCHITECTURE.md](docs/ARCHITECTURE.md)): a local 3B model may answer questions from retrieved memory and pick a tool. It must always have a rules fallback, its output must pass the validator and grounding checks, and **no LLM ever decides which of two conflicting reports is true**: conflicts are flagged for the person.
- No P2P mesh, CRDT text merge, IBLT/Merkle sync, Ed25519 signing (future scope only).
- No Pathway, n8n, Cloudinary or Omnidimension in the live path.
- No accounts/login/RBAC screens, no mobile rewrite, no Kubernetes/Kafka, no blockchain.
- Dashboard views: the original three plus **Companion** (chat with a visible trace) and **Control center** (judge controls, edge status, routing, audit, benchmark). No others.
- Nothing in the demo that needs venue Wi-Fi or a cloud API.

If you think something on this list is needed, write the case in the PR first.

## 5. Claims and honesty

- Every number in the README, slides or UI must come from a command (`bench.bench`, `demo.py rehearse`, `ml.train`, a test) and appear in `docs/BENCHMARKS.md` with its method.
- Numbers always carry their denominator: "50 of 50 scripted cases", "60 held-out notes".
- Report misses as misses (for example "38.2%, target 40%, missed"). Never round a miss into a hit.
- Banned claims: "runs on any edge device", "scales to millions", "military-grade / end-to-end encrypted", "zero data loss guaranteed", "AI understands everything", "revolutionary".
- Keep the "Known limitations" section in the README current.
- In research or analysis docs, keep the labels: **FACT**, **SOURCE-REPORTED CLAIM**, **ANALYST INFERENCE**, **RECOMMENDATION**, **NOT FOUND — REQUIRES VERIFICATION**. Cite a source for every FACT.

## 6. Credit third-party work

The hackathon rules require it. Any new library, model, dataset or asset must be added to the README "Credits" section in the same commit (name, licence, link, what we use it for).

## 7. Vocabulary (speak Qdrant's language precisely)

Use: "vector search engine", "Edge Shard", "mutable / immutable (mirror) shard", "partial snapshot", "hybrid query with RRF", "payload index", "`optimize()`", "named vectors". Use the component names: **Krypta** (private), **Hermes** (outbox + sync), **Agora** (fleet mirror), **Themis** (conflicts), **Argus** (router), **Chronos** (history), **Olympus** (dashboard). Say "flagged, never guessed" and "superseded, not deleted".

## 8. Engineering rules

- **Tests stay green.** `python -m pytest` must pass before every commit (45 tests today; the count only goes up). CI runs them on Ubuntu and Windows.
- New behaviour gets a test. Sync, outbox and Themis changes also need `demo.py rehearse --runs 3` passing.
- Any change to search, sync, the outbox, the router or the UI beats must be followed by `demo.py rehearse --runs 10` before the freeze. Log the Qdrant mode used.
- Keep `app.py` files thin; logic goes in `core.py` / modules. Shared code lives in `backend/common/` and is imported, never copied.
- Structured logs only (`backend/common/log.py`). No `print` in services.
- Windows is the demo platform: delete points, not shard folders; use `pathlib`; test on Windows before merging.
- Risky features (partial snapshots, float16 transport) ship behind a config flag with the old path as fallback, and only if 10/10 rehearsals pass.
- Scope: narrow and deep. Follow the cut rules in `Research Work/14_MVP_ROADMAP.md`.

## 9. Commit and repo hygiene

- Small, descriptive commits, each from the member who did the work (selection reads GitHub profiles).
- Commit messages: imperative subject ≤ 72 chars, body explains *why*. No attribution trailers (§0).
- The repo is public and rivals read it. Don't push final-round surprises before 30 Sep 23:59.
- Never commit `.env`, `runtime/`, `models/`, `logs/*.out`, or real personal data. Demo data uses synthetic names and numbers only.
- Pre-commit check (must print nothing):

```bash
git diff --cached | grep -niE "cl[a]ude|anthr[o]pic|co-authored-by|generated with"
```

## 10. Demo rules

- One laptop, Wi-Fi off, Qdrant Server in Docker, embedded mode as the fallback.
- Every beat has its own reset (`demo.py reset bN`); new beats must add a reset and a `play` check.
- Never demo live: model downloads, `pip install`, training, 1000-run simulations, multi-laptop networking (unless rehearsed at the venue).
- The 5-minute structure, beats and Q&A bank are in `Research Work/16`–`18`. Keep the UI and the script in sync.
