01 · The problem

Two technicians. One machine. No Wi-Fi.

Qdrant's own sync guide is a great start: local shard, queue, upload. But it uses wall-clock timestamps to decide what wins. On a factory floor, that is how a safety warning disappears.

STEP 1

The link drops mid-shift

Ravi and Meera both carry a tablet running the same edge memory. The factory Wi-Fi goes down. Nothing breaks: search and writes keep working locally, which is exactly what Qdrant Edge is for.

STEP 2

They write opposite things

Ravi notes that CNC-07 runs fine after a belt swap. A little later, Meera notes the spindle is vibrating and the machine should not run. Meera's tablet clock happens to be 9 minutes slow, as real device clocks are.

STEP 3

The link returns. A timestamp decides.

A timestamp-based sync compares 10:02 with 09:54 and keeps the "newer" one. That is the reference pattern in Qdrant's sync guide, and most sync databases.

STEP 4

The warning is silently gone

The naive merge keeps "runs fine" and drops the real warning. No error, no log line. Smaran flags both, lets the shift supervisor decide, and keeps the history of what each device believed.

02 · Qdrant Edge

Three shards on every device, three different promises.

Qdrant Edge is an embedded, in-process vector store. Smaran opens three EdgeShards per device and gives each one a job. Where a memory lives is its privacy policy.

SHARD 1

Krypta keeps what's private

Personal notes, phone numbers, IDs. This shard has no sync code path at all, so there is nothing to misconfigure: its contents cannot leave the device.

no outbox entrynever uploaded
SHARD 2

Hermes holds what's waiting to travel

New technician notes land here, and every write is also queued in a crash-safe outbox. When the link returns, Hermes carries them to the gateway.

mutablestatus transitions via set_payload
SHARD 3

Agora mirrors what the fleet knows

A local copy of Qdrant Server's collection: fleet manuals and every other device's synced notes. It is why a device can answer a question about a machine it has never touched, with the network off.

fed by a change feed
ONE PROCESS

No server needed to search

Each shard has a dense vector and a sparse BM25 vector, payload indexes on status, entity_key, machine and more. Because Edge has no background optimizer, Hermes runs optimize() on an idle timer.

    03 · Hybrid search, offline
    
Meaning and exact words, in about 3 milliseconds.

    
A technician types "CNC-07 bearing noise". A dense vector finds notes that mean the same thing. BM25 finds the exact part number. Smaran fuses both.

  

  

    

      
STEP 1
Embed on the device
The query is embedded locally by bge-small (384 dimensions) and tokenised by Qdrant Edge's built-in Bm25 encoder. Its token ids match Qdrant Server's BM25, so the server can score device-made sparse vectors without re-indexing.

      
STEP 2
Two ranked lists, across all three shards
One global dense list (cosine is comparable across shards) and one global BM25 list. Dense wins on paraphrase; BM25 wins on identifiers like LATHE-03.

      
STEP 3
Fuse with RRF
Reciprocal Rank Fusion rewards a memory that ranks well in either list. Both agree on the bearing note, so it rises to first.
We first tried native fusion per shard, then merging shard lists. It let a one-note Krypta outrank the real answer, because every shard's #1 counted the same. Fusing two global lists fixed it.

      
STEP 4
Measured, not claimed
1,000 offline queries over 2,000 memories: 3.04 ms p50, 3.98 ms p95. Including query embedding: 8.3 ms p50. On 40 golden queries hybrid reaches hit@5 0.975 vs 0.95 for dense-only or BM25-only.

    04 · Argus · what stays local, what syncs
    
Rules first. A model second. Every decision explains itself.

    
Problem Statement 3 asks the device to dynamically decide what stays local and what syncs. Argus does it in three layers, in a fixed order, and stores the reason next to every memory.

  

  

    

      
LAYER 1
PII rules always win
Phone numbers, emails, Aadhaar and PAN patterns force a note into Krypta, with confidence 1.0. No model can override this. The gateway runs the same rules again as defence in depth. Try it on the right.

      
LAYER 2
A learned classifier proposes
A logistic-regression model on bge-small embeddings says private, sync or drop, plus a criticality level. Safety keywords can raise criticality. When the model is unsure, the note stays local. Status updates are never dropped.
98.3% on 60 held-out notessafety recall 0.9

      
LAYER 3
Dedup against fleet knowledge
If a note is a near-duplicate of something already in Agora (cosine ≥ 0.95), it's dropped instead of syncing. That is where much of the bandwidth saving comes from.

    05 · Hermes · the outbox
    
Safety-critical first. Crash-safe. Never twice.

    
Links are weak and devices die. Hermes is a SQLite-backed outbox, so a hard kill loses nothing that was acknowledged, and the gateway ignores anything it has seen.

  

  

    

      
STEP 1
Offline writes queue up
Five notes are written with the link down. Each one gets an op_id, is stored in Hermes, and joins the outbox with a criticality.

      
STEP 2
The link returns: critical goes first
On a weak connection, order matters. The safety-critical note is sent before the routine ones, so the warning about the smoking press reaches the fleet first.

      
STEP 3
Kill it mid-drain
The gateway stored a batch, but the device died before it heard the acknowledgement. Qdrant Edge keeps recent writes in memory until a flush, so a hard kill can lose them. SQLite is the durable log: outbox, a local Krypta journal, and Agora is re-pulled after an unclean shutdown.

      
STEP 4
Resend. Zero duplicates.
Point ids are uuid5(op_id), and the gateway skips any op it has seen. The unacknowledged batch is sent again, and the server ends up with each memory exactly once. In the rehearsal, 3 of 3 ops were resent and 0 duplicate memories appeared.

    06 · Themis · deciding what's true
    
Version vectors tell newer from concurrent.

    
A clock can lie; a version vector cannot. It counts how many writes from each device a version has seen. That is enough to know whether one report supersedes another, or whether they were written independently and must both be kept.

  

  

    

      
CASE 1
An update: one dominates
Meera wrote after seeing Ravi's report, so her vector is ≥ his in every position. Hers is newer. His is superseded, kept in history but hidden from search.

      
CASE 2
A conflict: neither dominates
Each device wrote while the other was offline. Ravi has seen 1 write from A and none from B; Meera the reverse. Neither is ≥ the other, so they are concurrent. Themis marks both contested. It never guesses.

      
CASE 3
The supervisor decides
A new version is written by someone who has seen both, so its vector dominates both. The conflict resolves cleanly and the history stays.

      
THE GUARANTEE
Order can't change the answer
Themis computes statuses from the set of versions, so delivery order and duplicates don't matter. Over 1,000 random runs with 5 devices, random offline edits and duplicate sends, all replicas ended identical, and 0 concurrent edits were lost.
1000 / 1000 convergedsame rules on device and gateway

    07 · Edge to Qdrant Server
    
A real server, a real change feed, a lot fewer bytes.

    
The gateway is a thin service in front of Qdrant Server. It resolves conflicts, writes points with qdrant-client, and hands every device a feed of what changed.

  

  

    

      
UP
Idempotent batches to one collection
Device outboxes post batches to the gateway. Each op becomes a point in a single-shard collection with a named dense vector, a sparse bm25 vector with the IDF modifier, and payload indexes on status and entity_key.

      
DOWN
A change feed keeps Agora fresh
Devices pull /changes?since=…, which sends only changed points, and upsert them into Agora. Statuses are re-resolved locally so every replica agrees with the server.

      
ESCALATE
Ask the cloud when local isn't enough
If the best local dense score is under a threshold, the device asks Qdrant Server: a Prefetch on dense and BM25, fused with FusionQuery(RRF). The result says whether it was answered locally or escalated.

      
BYTES
Selection plus float16
Not syncing private and duplicate notes saved 38.2%, which alone missed our 40% target. Sending dense vectors as base64 float16 instead of JSON floats takes the total to 85.7%, with a round-trip error under 1e-3.

Read thisWhat these numbers are not
    
        
  • Data is synthetic or team-written: 2,000 generated memories, 40 golden queries, 60 hand-written test notes. Treat them as indicative, not as a general benchmark.
    • 
        
  • The conflict benchmark uses cases built to break last-writer-wins. It shows Themis is correct, not that real fleets conflict at this rate.
    • 
        
  • Devices are processes on one machine; "offline" is a software link switch.

      
Misses, reportedWhat fell short
    
        
  • Selection alone saved 38.2% of bandwidth, under the 40% target. Float16 transport did the rest.
    • 
        
  • Label agreement (Cohen's κ): residency 1.00, criticality 0.66, below our 0.7 target. The second labeller was Claude, an AI model, not a human.
    • 
        
  • Partial-snapshot refresh of Agora worked but saved no bandwidth at this size, so we don't claim it.
